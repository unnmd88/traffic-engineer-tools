# Предложения по развитию

## Общий механизм попыток `poll()`

Статус: предложение для следующего обсуждения. Изменения ниже пока не реализованы.

### Контекст

Проба — произвольный сценарий. Один `do_work()` может выполнять несколько разных
запросов, вычисления и условные действия. Проба сама решает, использовать ли общий
`poll()` для конкретной операции.

Сейчас цепочка простой SNMP-пробы выглядит так:

```text
Worker → Probe::do_work() → poll(&config, &adapter) → Pollable::poll()
```

- `Pollable::poll()` выполняет одну попытку запроса.
- Общая функция `poll()` управляет попытками, таймаутами и задержками.
- `do_work()` выполняет весь сценарий и возвращает `Result<ProbeOutcome, ProbeError>`.

### Что сохранить

Алгоритм общего `poll()` нужен: таймаут одной попытки, выход при первом успехе,
повторы временных ошибок, немедленное завершение при фатальной ошибке и сбор
сведений о попытках и длительности. Эта логика не должна дублироваться в пробах.

### Предложение: передавать операцию вместо обязательного `Pollable`

Рассмотреть API, принимающий замыкание, которое создаёт future новой попытки:

```rust
let response = poll(&config, || async {
    client
        .get_many(&oids)
        .await
        .map_err(classify_snmp_error)
})
.await?;
```

Это эскиз будущего вызова; текущая функция пока принимает `&impl Pollable`.
Для нескольких операций внутри сценария не понадобятся дополнительные типы
и реализации `Pollable` только ради передачи запроса в механизм попыток.

Для запросов через общие ссылки базовые ограничения могут выглядеть так:

```rust
F: FnMut() -> Fut,
Fut: Future<Output = Result<T, AttemptError>>,
```

Передавать нужно фабрику future: каждый вызов создаёт новую попытку.
Одну уже созданную future нельзя использовать повторно для повторения запроса.

До выбора окончательной сигнатуры проверить:

- Запросы клиентов с `&self` и с `&mut self`. Простого `FnMut() -> Fut` может
  не хватить для future, заимствующей изменяемое состояние самого замыкания.
- Ограничения `Send`, необходимые для исполнения воркера через `tokio::spawn`.
  Не добавлять `Sync` и `'static` без необходимости.
- Поведение клиента после отмены попытки по таймауту: отброшенная future
  не отменяет команду, уже отправленную устройству.
- Допустимость повторов конкретной операции. Повтор SET одного значения
  и повтор команды «переключить на следующую фазу» имеют разную семантику.

Повторы должны охватывать выбранную операцию. Автоматический повтор всего
составного сценария может заново выполнить уже успешные команды.

### Когда `Pollable` всё же полезен

Трейт уместен, если запросы станут отдельными сущностями: например,
`SnmpGetRequest` и `ModbusReadRequest`, которые используются независимо от проб.
Сейчас `Pollable` реализует сама SNMP-проба, совмещая сценарий и одну операцию.
Выделять самостоятельные типы запросов только ради общего `poll()` необязательно.

`#[async_trait]` возвращает `Pin<Box<dyn Future + Send + ...>>` даже при
generic-параметре `A: Pollable`. При выборе API учитывать необходимость такого
упаковывания; для сетевых операций само по себе оно не является критической проблемой.

### Ошибка на границе количества попыток

В `poll.rs` используется `retries().saturating_add(1)` для `u8`.
При `retries = 255` выполняются 255 попыток вместо ожидаемых 256.
При этом `AttemptConfig::budget()` рассчитывает бюджет 256 попыток.

Варианты исправления:

- расширить тип числа попыток и связанных полей `Response` / `PollErrorContext`;
- либо явно ограничить `retries` при создании `AttemptConfig`.

Добавить проверку граничного значения и согласованности с бюджетом.

### Проверки при изменении API

- Успех прекращает последующие попытки; проверить успех после временных ошибок.
- Фатальная ошибка прекращает попытки без лишней задержки.
- Каждая попытка получает отдельный таймаут и новую future.
- Задержка выполняется только между попытками.
- Сохраняются сведения о предыдущих неудачных попытках.
- Составная проба может выполнить несколько разных операций через общий механизм.
- Сценарий может полностью обходиться без `poll()` и `Pollable`.
