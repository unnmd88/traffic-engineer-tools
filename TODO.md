# План развития контракта monitor

## Порядок работы

Перед каждым шагом давать краткую сводку предстоящих изменений.
После реализации и проверок объяснять результат и останавливаться.
Только после пользовательского «ок» делать коммит и переходить
к следующему шагу. Не объединять несколько шагов без согласования.

Сборка и выполнение Application уже разделены в коммите `bc91189`.

## Принятые решения

- Выбор расписания повторяющегося запроса выразить через PollSchedule:
  `FixedRate { period }` и `FixedDelay { delay }`.
- Расписание принадлежит повторяющемуся сценарию, не глобальному TaskConfig.
- `limit` считает полные выполнения сценария. Полный запрос, включая все
  внутренние повторы, расходует одну единицу независимо от успеха или
  исхода NoResponse после таймаутов. `limit = 0` означает отсутствие лимита.
- Счётчик выполнений и проверку limit оставить на уровне задачи/монитора.
- Новую обёртку VersionedTaskConfig не вводить.

## Шаг 2. PollSchedule

- [ ] Реализовать FixedRate: сроки образуют сетку `origin + n * period`
  на монотонных часах, длительность запроса не сдвигает сетку.
- [ ] Реализовать FixedDelay: следующий запрос назначается через delay
  после завершения предыдущего полного запроса с его повторами.
- [ ] До реализации уточнить оставшиеся детали. Предложение для FixedRate:
  выполнять последовательно, просроченные старты пропускать и ждать
  ближайшей будущей точки сетки, без догоняющих запросов.
- [ ] Согласовать режим по умолчанию и преобразование текущего interval
  из конфигурации CLI. Текущее поведение соответствует FixedDelay;
  исторический смысл interval соответствовал FixedRate.
- [ ] Определить первый запуск и resume. Сейчас они ждут полный interval.
- [ ] Пересмотреть ограничение `interval >= attempt.budget()`: для
  FixedDelay оно не требуется; для FixedRate необходимость зависит от
  политики пропусков. Проверка бюджета сама по себе не устраняет дрейф.
- [ ] Проверить расписание виртуальным временем и исполнителем без сокетов.
- [ ] После объяснения результата и пользовательского «ок» создать коммит.

Координация сохранит собственное расписание по общей эпохе. Локальная
монотонная сетка повторяющихся запросов не синхронизирует разные объекты.

## Проверки

После каждого изменения кода выполнять соответствующие проверки компиляции,
форматирования, линта и контрактов без сокетов.

сетевые тесты только собирать через --no-run. Полный прогон с UDP отложен
до отдельного указания пользователя.
